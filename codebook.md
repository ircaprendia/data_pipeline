## Course taxonomy is version-pinned — read the course/module flags with caution

*Added 2026-06-09 after a drift audit against the bot knowledge base (`B - aprendia knowledge base.md`, latest version).*

The course and module flags in this codebook (`select_reading`, `maths_mod*_start`, `classroom_mod*_start`, and the rest) are **version-pinned legacy detectors**, not a live product map. They were written against an earlier bot taxonomy. The bot has since drifted structurally — courses added, dropped, renamed, and renumbered — so the flags are accurate only for the era they were written against. Three corrections to the labels below: Reading is a now-historical course; the "Classroom management" flags actually detect the SEL / Healing Classroom course; and the Maths module structure predates a restructuring. Detail is annotated inline in each section.

The durable way to read these datasets separates two kinds of thing the wide flags conflate:

- **Version-stable structural primitives.** `has_start_phrase`, `has_completion`, `has_quiz`, onboarding-present, and reminder-detection (`start_direction`) detect *that* a module started, a quiz happened, or onboarding occurred — independent of which course or what number. They survive wording drift, unlike the fields below. **Correction, 2026-09-08:** "trust these" overstated it — surviving drift is a recall property, not a precision guarantee. All three are confirmed live (see "Bot interaction flags" below) but explicitly unvalidated for precision; treat as live, not as trusted.
- **Course-and-module identity — do not read as current.** "Reading module 3", "Maths M2", the SEL-mislabelled `classroom_mod*` — this is what rots with each bot version. The forward direction (Track 1.5 / Track 4) is to stop matching a frozen enum and instead recover the course/module title as a data field whose value is whatever the transcript says.

No KB version history is known to exist, so the legacy flags cannot be date-bounded to specific bot versions precisely. Until one surfaces (a Track 0 ask), treat any specific course list as defensive, not authoritative.

*Update 2026-07-01: the durable course map now exists as `research/course_taxonomy/` — `course_lineage.csv` (5 stable course concepts), `course_version.csv` (every known generation, dated where possible), and `module_crosswalk.csv` (bridges every raw `*_start` column, or its explicit absence, to a version). Read the wide flags below through that crosswalk: it is the authoritative statement of which legacy flag maps to which course generation, and which of the product team's current courses have any tracking at all. See its `README.md` for the join path and open questions.*

### Country

Two distinct country fields — **do not conflate them**.

| Variable | Type | Description | Notes |
|----|----|----|----|
| `country` | chr | **Bot instance** used | Which deployment the message belongs to: `"nigeria"`, `"ecuador"`, or `"niger"`. Derived from the *bot's* phone number via the per-country config filter in `clean_messages()` — not from the user's number. This is the aggregation grain and the classification / dashboard slice key. Present in all four datasets (the `contact_id × country` grain). |
| `user_phone_country` | chr | **Country of the teacher's phone** | Country implied by the dialing code of the teacher's *own* number (the non-bot side: `from` on Incoming, `to` on Outgoing). Values: `"Nigeria"`, `"Niger"`, `"Ecuador"`, `"US/Canada"`, `"Other"` (a recognised but unlisted dialing code), or `NA` (unparseable / local-format number with no code). Derived in `clean_messages()`; the raw number is discarded, so no phone number is retained. Constant within a contact, so it is carried through to `session_data` and `contacts_data` via `first()`. The code list is easily extended. |

`country` answers "which bot did this message go through"; `user_phone_country` answers "where is the teacher". They can differ — a teacher with a Nigerian number using the Niger bot reads `country = "niger"`, `user_phone_country = "Nigeria"` — which is the cross-border signal of interest.

## Level 2b: Session with churn/reactivation (`session_data_long`)

`session_data_long` extends `session_data` by adding churn and reactivation flags derived from inter-session gaps. It also includes synthetic "final gap" rows appended to each user's session history to detect churn after their last observed session. It has more rows than `session_data` because of these synthetic rows (see the count table above).

All variables from `session_data` are present. The following variables are added:

| Variable | Type | Description | Notes |
|----|----|----|----|
| `gap_secs` | dbl | Gap in seconds since previous session | `session_start` minus previous `session_end`. NA for user's first session |
| `churned` | lgl | Churn flag | TRUE if `gap_secs > churn_threshold` (14 days). Marks the session that *follows* a churn gap. NA for first session |
| `churned_time` | dttm | Churn timestamp | End of previous session plus 14 days — backdated to day 15 of the inactivity gap. NA if not churned |
| `churned_msg_day` | dbl | User-relative day of churn | `message_day + 14` for the session preceding the churn gap. NA if not churned |
| `churned_msg_week` | dbl | User-relative week of churn | `message_week + 2` for the session preceding the churn gap. NA if not churned |
| `reactivated` | lgl | Reactivation flag | TRUE if the previous gap exceeded the churn threshold — this session is the first after a churn event |

**Important notes on churn logic:** - `churned = TRUE` on a session means the gap *before* this session exceeded 14 days — the user had churned and this session is their return - `reactivated = TRUE` also marks this return session - `churned_time`, `churned_msg_day`, and `churned_msg_week` are backdated to 14 days after the previous session end, not to the start of the return session - This dataset is the source for `churn_count` and `reactivate_count` in `contacts_data`

## Level 4: Onboarding schema (`onboarding_attempts`, `onboarding_answers`)

*Added 2026-10-08. Nigeria only. This level replaces the event schema, which is no longer live and is no longer documented here. An engagement schema, covering courses, modules and quizzes, is in development and will be documented at this level when it exists. The two tables below are built by an analysis-side script from the reading agents' results files. They are not produced by the scripts in this repository, and the tables are not published. The method is described in [onboarding_schema.md](onboarding_schema.md).*

Onboarding is read from each conversation by a language model, which records where onboarding started, how far it got, and what the teacher answered. Two tables hold the result at two grains. Both hold the full history of every prompt version that has been run. "Current" is worked out when the table is queried, as the highest prompt version for each key, and is never stored. Rows from the audit sample are kept and tagged, not collapsed. Both tables join to `contacts_data` on `contact_id`.

**Coverage.** Reading proceeds in batches, so the tables cover only the teachers read so far. The absence of a row does not mean a teacher did not onboard.

**What is not here.** The course, module, quiz and toolkit events that the event schema once recorded are not currently available as a table. The engagement schema is intended to provide them.

### `onboarding_attempts` — one row per contact, episode, source and agent group

| Variable | Type | Description | Notes |
|----|----|----|----|
| `contact_id` | chr | Join key to `contacts_data` | |
| `episode_number` | chr | The episode's number within the contact | Taken from the detector. For a contact with no detected start where onboarding was found, 1 by convention. `NA` where the contact never onboarded |
| `source` | chr | Which task produced the row | `known_episode` (the detector found a start) or `no_start_found` (it did not) |
| `agent_group` | chr | Label of the reading group, eg `K1`, `Z3` | Labels repeat across batches, so they do not identify a run. Use `source_file` |
| `prompt_version` | chr | Version of the prompt that produced the row | eg `known_v1.2`, `no_start_v1.4` |
| `extracted_date` | date | When the reading was done | |
| `is_audit_pass` | lgl | The row belongs to the second-reading audit sample | About one in ten items |
| `source_file` | chr | Name of the results file the row came from | Identifies the batch |
| `completeness` | chr | `completed`, `partial` or `abandoned` | Where onboarding was found |
| `completeness_fraction` | chr | Answers recorded over questions asked, eg `3/5` | The denominator is the question set actually observed in that episode. The rule for counting a rejected-then-recovered answer was not applied identically in early batches |
| `furthest_question_reached` | chr | The last question the teacher reached | `none` if no question was presented |
| `genuinely_never_onboarded` | chr | `yes` or `no` | `no_start_found` rows only |
| `never_onboarded_category` | chr | Why onboarding did not happen | `no_start_found` rows only. Values below |
| `engagement_level` | chr | Rough use level of a never-onboarded contact | `no_start_found` rows only |
| `total_message_count` | int | The contact's message count at the time of reading | `no_start_found` rows only |
| `opening_text_quoted` | chr | The bot's opening line of an onboarding the detector missed | `no_start_found` rows only. Used to improve the detector |
| `opening_text_message_id`, `opening_text_message_num` | chr | Where that opening line sits | |
| `possible_bot_bug` | chr | One sentence on any bot fault the reader saw | Blank if none. Free text |
| `pii_exposure_note` | chr | Where a teacher volunteered personal information | Blank if none. Free text |
| `safeguarding_flag` | chr | `yes` if the reader saw a possible safeguarding concern | |
| `safeguarding_message_id`, `safeguarding_quoted_text`, `safeguarding_description` | chr | The message, the teacher's words and a one-line description | Blank if no flag. Quotes conversation, so these columns are not published |
| `detector_generation`, `detector_status`, `detector_start_time`, `detector_ended_at`, `detector_outcome`, `detector_boundary_method` | chr | The pipeline detector's own record of the episode | Joined from the detector's episode table for comparison. Where the reader's `completeness` and the detector's outcome disagree, the reader's judgement is used |
| `agent_generation` | chr | Which onboarding script the questions asked point to | Derived when the table is built, from the fields the reader marked as asked: `old (6q)`, `new (5q)`, `hybrid` (questions from both scripts) or `undetermined` (only gender and grade level, which both scripts share) |

### `onboarding_answers` — one row per contact, episode, field and agent group

Rows exist only where a field was asked, so a contact who never onboarded has none.

| Variable | Type | Description | Notes |
|----|----|----|----|
| `contact_id`, `episode_number`, `source`, `agent_group`, `prompt_version`, `extracted_date`, `is_audit_pass`, `source_file` | | As in `onboarding_attempts` | |
| `field` | chr | The question | Values below |
| `asked` | chr | `yes` or `no` | |
| `answer` | chr | The normalised answer | The exact allowed value for closed-set fields. Free-text fields are recorded as given, lightly cleaned. Blank if unanswered |
| `quoted_text` | chr | The teacher's words, verbatim | Quotes conversation, so this column is not published |
| `message_id`, `message_num` | chr | The message the answer came from | `message_num` orders messages within a contact. Never use time sent, which is missing for incoming messages |
| `n_attempts` | int | Genuine attempts at this question | The prompt defines what counts. Greetings and duplicate resends do not |
| `missing_reason` | chr | Why there is no answer | One of the seven values below. Blank if answered |

### Allowed values

**`field`:** `gender`, `students_grade_level`, `class_size`, `instructional_materials_tier`, `learner_level_descriptor` (the newer five-question script); `student_ages`, `main_challenge`, `materials_freetext`, `priority_outcome` (the older six-question script, with `gender` and `students_grade_level` shared).

**Closed-set `answer` values.** `gender`: `male`, `female`, `other`, `prefer_not_to_say`. `instructional_materials_tier`: `very_limited`, `few_materials`, `some_teaching_aids`, `many_materials`. `learner_level_descriptor`: `many_need_extra_help`, `different_levels`, `most_follow_lesson`, `most_learn_quickly`.

**`missing_reason`:** `not_applicable_to_generation` (the script in use has no such question), `asked_never_answered`, `answered_but_rejected_by_bot` (the teacher gave a good-faith answer that the bot's own validation did not accept), `skipped_by_bot_error` (the bot moved past a question it should have asked), `never_reached` (onboarding was abandoned before this question), `conversation_ended_before_reached`, `unreachable_episode_derailed` (the flow was permanently abandoned for another feature).

**`never_onboarded_category`:**

| Value | Meaning |
|----|----|
| `consent_gate_bypassed` | No consent notice was affirmed, yet a course was reached |
| `went_straight_to_course` | Consent was affirmed in reply to the disclosure text, and onboarding was skipped |
| `affirmed_no_access_granted` | Consent was affirmed, and nothing further was granted |
| `stalled_at_consent` | A consent notice was shown, never affirmed, and no access followed |
| `used_confound_feature` | A side feature (the lesson-plan builder or a short topic intake) was used instead of onboarding |
| `bypassed_via_adhoc_qa` | The teacher received ordinary question-and-answer replies from the start, with no setup step |
| `too_few_messages` | Too little conversation to tell. Used only when no other category can be decided |
| `genuine_trigger_boilerplate_reuse` | The onboarding opening line was reused as a menu label, with no questions following |

Where a history fits more than one category, the reader works down a fixed priority order and stops at the first that applies. The order is set out in [onboarding_schema.md](onboarding_schema.md).
